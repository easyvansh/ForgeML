The final project should be **one research-grade ML systems project with a narrow thesis**, not “implement 12 famous papers.” The papers should form a chain where each one motivates the next engineering decision.

# Final Project

## **ForgeML: A GPU-Native Transformer Training Runtime for Studying Compute-Efficient Learning**

**One-line description**

> Build a small deep-learning framework from first principles—automatic differentiation, optimizers, Transformer layers and custom CUDA attention kernels—and use it to experimentally study how **model scale, training data, context length and GPU memory behavior interact under limited compute**.

This gives you four signals simultaneously:

**ML theory + ML experimentation + GPU/systems engineering + research methodology.**

That combination is much stronger for AI/ML roles than either a pure CUDA project or a pure model-training project.

---

# 1. The central research question

Everything should revolve around:

> **Under a fixed, limited compute budget, how should small Transformer language models trade model size, training tokens and context length—and at what point do IO-aware GPU optimizations materially change that trade-off?**

Then split that into four precise research questions.

### RQ1 — Correctness

> Can a minimal autodiff/runtime implementation reproduce PyTorch numerical behavior closely enough to train Transformer models reliably?

### RQ2 — Optimization

> How do SGD, Adam and AdamW affect convergence and generalization in small Transformer language models?

### RQ3 — Systems

> As context length increases, where does standard attention become bottlenecked by memory movement, and how much can an IO-aware tiled implementation recover?

### RQ4 — Scaling

> Under fixed compute budgets, how do model size and training-token allocation affect validation loss at small scale, and do the qualitative behaviors reported by scaling-law literature appear?

These questions connect naturally.

# 5. Paper 5 — FlashAttention

## This is the centerpiece.

**Dao et al., 2022**

FlashAttention identifies memory movement between GPU memory levels as a crucial attention bottleneck and uses tiling to reduce HBM reads/writes while computing exact attention. ([arXiv][4])

This connects the ML project to NVIDIA-style systems engineering.

Your implementation progression should be:

Call V3 something like:

> **FlashAttention-inspired IO-aware tiled attention**

That is accurate.

# 6. Paper 6 — FlashAttention-2

Use it as a **systems analysis paper**, not something you promise to fully reproduce.

FlashAttention-2 improves work partitioning across thread blocks and warps and reduces unnecessary non-matmul work and shared-memory communication. The published work reports significantly higher utilization than the first implementation on its target hardware. ([DOI][5])

Use it to motivate experiments around:

```text
block size
warp arrangement
tile size
shared memory usage
occupancy
register pressure
```

You might implement **one FA2-inspired scheduling/work-partitioning improvement**.

That's enough.

# 7. Papers 7 + 8 — Scaling Laws and Chinchilla

These should be treated together.

Kaplan et al. identified empirical power-law relationships connecting language-model loss with parameters, dataset size and compute. ([arXiv][6])

Hoffmann et al. later investigated compute-optimal training and found that, within their studied large-scale regime, increasing model size and training tokens together gave a better compute allocation than simply making models increasingly large. ([arXiv][7])

You are **not reproducing Chinchilla**.

You're testing:

> Does a qualitatively similar compute/data/model-size tradeoff appear at 1M–50M parameter scale?

That is scientifically much more respectable.

# 10. Component B — Autograd

Every differentiable operation stores enough state to calculate its backward pass.

For:

$$
C=AB
$$

derive:

$$
\frac{\partial L}{\partial A}
=
\frac{\partial L}{\partial C}B^T
$$

and:

$$
\frac{\partial L}{\partial B}
=
A^T\frac{\partial L}{\partial C}
$$

Implement:

```python
x = Tensor(..., requires_grad=True)
w = Tensor(..., requires_grad=True)

y = x @ w
z = relu(y)
loss = z.mean()

loss.backward()
```

### Technical prowess #1

Don't simply demonstrate that it runs.

Implement automated **gradient checking**.

Compare:

```text
ForgeML analytical gradient
          vs
finite differences
          vs
PyTorch autograd
```

Report:

$$
\text{relative error}
=
\frac{|g_{forge}-g_{reference}|}
{|g_{forge}|+|g_{reference}|+\epsilon}
$$

This is exactly the kind of detail that makes the repo look serious.
